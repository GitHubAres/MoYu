# 热点雷达 · 第三方聚合 API 调研与技术选型结论

> **文档定位**：本报告为墨语 MoYu「热点雷达」功能模块 Milestone 0 (M0) 的技术调研成果交付件，亦作为 docs/开发计划-热点雷达.md「九、风险与回退」与「M0 里程碑」的正式决策支撑。  
> **调研日期**：2026-10-12  
> **调研目标**：评估起点中文网、番茄小说、晋江文学城三大主流网文平台热榜是否存在可用的第三方聚合 API，明确首版技术选型路径（第三方 API vs 自写爬虫），并输出可落地的抓取可行性评估与抓取要点。

---

## 一、调研背景与评估基准

在墨语 MoYu 创作工作台的技术框架下，热点雷达旨在为作者提供题材趋势、热榜异动与立项灵感。按照《热点雷达 · Codex 开发指引与任务书》（A3 专项约束）与《墨语产物交付规范》：
1. **字段覆盖度基准**：必须覆盖各平台热榜的「作品名（	itle）」、「排名（
ank）」、「题材标签（genre_tags）」与「热度值（heat）」。
2. **安全合规基准**：严格只采集公开热榜元数据，绝不采集/存储正文或小说章节内容；
3. **运维与可用性基准**：优先零成本/低成本、稳定性高、免授权争用或低维护成本的方案。

## 二、第三方聚合 API 调研现状

针对国内商业数据服务平台、开发者开放平台以及开源社区聚合项目的调研评估结果如下：

| 数据平台 / API 服务 | 起点中文网 | 番茄小说 | 晋江文学城 | 商业模式 / 费用 / 鉴权 | 核心缺陷与可用性结论 |
|---|---|---|---|---|---|
| **天行数据 (TianAPI)** | ❌ 无网文榜单 | ❌ 无网文榜单 | ❌ 无网文榜单 | Token 鉴权 / 按次计费 | 仅有微博/百度/知乎等综合社媒热搜，完全无网文垂类排行。**不可用** |
| **聚合数据 (Juhe)** | ❌ 无网文榜单 | ❌ 无网文榜单 | ❌ 无网文榜单 | AppKey / 商业套餐 | 仅涵盖新闻、天气、生活服务等传统接口，无小说热榜产品。**不可用** |
| **ALAPI / RollToolsApi / Uapis** | ❌ 无网文榜单 | ❌ 无网文榜单 | ❌ 无网文榜单 | API 密钥 / 免费套餐 | 均为通用开发工具聚合类 API，无网文排行接口。**不可用** |
| **百度热搜 / 微博热搜 (读书/小说榜)** | ⚠️ 仅极少量混合条目 | ❌ 无法区分平台 | ❌ 无法区分平台 | 需自建解析器 | 属于全网泛阅读热度，不包含网文垂直平台排名、分类标签与月票/读完率等专业维度。**不可用** |
| **开源第三方网文聚合项目 (GitHub/Gitee)** | ⚠️ 多数失效/已停更 | ⚠️ 多数失效/已停更 | ⚠️ 多数失效/已停更 | 自托管服务 | 社区多年前的爬虫聚合 API（如基于 Node/Python）因平台反爬风控升级（如起点的 WAF 拦截、番茄的自定义字体反爬）95% 以上处于弃坑不可用状态，且引入自建 API 服务会增加桌面端用户的运维部署门槛。**不可用** |

### 调研结论
**市场上目前不存在能够同时稳定覆盖「起点、番茄、晋江」三平台公开热榜元数据（书名、排名、题材标签、热度）的标准化第三方商业或公益聚合 API。**

## 三、架构决策与选型路线

### 决策结果：**正式触发 M0 回退机制 —— 全面采用「自写轻量爬虫兜底」方案**

### 选型理由：
1. **自主可控、零依赖**：自写爬虫直接随墨语本地服务运行，无需用户配置额外的第三方 API Key，无需承担商业数据平台的断供、限流与收费风险。
2. **数据完整性更优**：直接抓取三大网文官方公开站点，能获取最准确的官方排名、原汁原味的题材标签（如起点的「东方玄幻」、晋江的「原创-言情-架空历史-仙侠」）及平台原生热度指标。
3. **架构轻量合规**：仅抓取公开排行榜的只读静态/SSR 页面元数据，完全不触碰鉴权接口、用户隐私或正文章节，符合平台安全边界与墨语 A3 专项约束。

## 四、三大平台公开热榜抓取可行性评估与实施要点

经本地实测与网络链路嗅探，三大网文平台公开排行榜的技术特征与抓取要点总结如下：

### 1. 起点中文网 (qidian)
- **公开页面形态**：
  - PC 端页面（https://www.qidian.com/rank/hotsales/）：当前启用了 WAF 人机校验与动态 JS 屏障，直连 HTTP 请求常返回 HTTP 202 Accepted 或安全验证页。
  - **M 站公开页面（https://m.qidian.com/rank/hotsales/、https://m.qidian.com/rank/yuepiao/）**：**抓取可行性极高！**
- **登录依赖**：**无需登录**，全公开访问。
- **反爬与风控**：普通 HTTP GET 携带移动端 User-Agent 即可直连获取（HTTP 200）。
- **数据结构与 DOM 稳定性**：
  - 页面采用 SSR / Vite 服务端渲染，页面内部直接内联注入完整的 JSON 数据包：<script>{"pageContext":{"pageProps":{"pageData":{"records":[...]}}}}</script>。
  - 数据字段结构清晰规范：
    - 作品名：
ecords[i].bName（明文字符串）
    - 排名：
ecords[i].rankNum（整数 1~N）
    - 一级题材：
ecords[i].cat（如「玄幻」）
    - 二级题材：
ecords[i].subCat（如「东方玄幻」）
    - 作者：
ecords[i].bAuth
    - 字数/简介：
ecords[i].cnt、
ecords[i].desc
- **抓取要点**：
  - 使用标准 httpx.AsyncClient，请求头配置移动端 UA（如 iPhone / Safari）；
  - 用正则 
e.search(r'\{"pageContext":.*\}', html) 提取 JSON 并 json.loads，100% 免疫前端 DOM 类名变动，解析速度极快且极度稳定。

---

### 2. 番茄小说 (anqienovel)
- **公开页面形态**：
  - 官方公开热榜主页：https://fanqienovel.com/rank。
- **登录依赖**：**无需登录**，全公开访问。
- **反爬与风控**：
  - 存在**自定义 WebFont 字体加密混淆**（页面中的部分核心字形使用自定义 unicode 编码，如 \ue491 替换汉字）。
  - 但**热度与榜单次序完全公开明文**：
ead_count / bstract / 内部分类 ID 等均以结构化明文暴露。
- **数据结构与解析策略**：
  - 页面内嵌 window.__INITIAL_STATE__ = { ... }，榜单直接位于 state["rank"]["book_list"]。
  - 字段覆盖：
    - 排名：条目下标或 currentPos
    - 在读/热度：
ead_count（整数，如 287362，代表全网在读人数，热度衡量极高价值）
    - 分类标签：curent_category_id / pos_category_id，可通过轻量映射字典还原；
    - 书名明文降级提取：
      - *策略 A*：通过书籍详情页 https://fanqienovel.com/page/{bookId} 的 <title> 标签快速提取（如 <title>父皇他两辈子都在装完整版在线免费阅读...</title>，SEO 标题不受字体反爬混淆，为 100% 纯明文字符串）。
      - *策略 B*：针对常用字建立轻量 glyph 映射表或通过移动端公开榜单 API 直取。
- **抓取要点**：
  - 请求带标准现代桌面 UA；
  - 榜单元数据直接从 window.__INITIAL_STATE__ 获取；
  - 热榜前 20 条作品利用详情页 SEO 标题补全明本书名，兼顾高准确性与低抓取频次。

---

### 3. 晋江文学城 (jjwxc)
- **公开页面形态**：
  - 经典榜单页：https://www.jjwxc.net/topten.php?orderstr=3（总分榜）、orderstr=1（月榜）等。
- **登录依赖**：**无需登录**，全公开静态页面。
- **反爬与风控**：
  - **几乎无反爬风控**。只要正常设置请求头 User-Agent，HTTP GET 即返完整的 HTML 页面（编码为 GB18030 / GBK）。
  - 访问频控友好，单次请求即可返回 100~300 条完整榜单记录。
- **数据结构与 DOM 稳定性**：
  - 晋江属于二十年未大改的传统经典纯 HTML <table> 表格布局，DOM 结构极其坚固稳定，几乎不会发生突发改版。
  - 表格每行 <tr> 顺序呈现：
    - 第 1 列：排名（1, 2, 3...）
    - 第 2 列：作者（<a href="oneauthor.php?authorid=...">江好桃</a>）
    - 第 3 列：书名（<a title="滂沱雨[娱乐圈]" href="onebook.php?novelid=...">）
    - 第 4 列：题材类别（明文，如 原创-言情-近代现代-爱情、原创-言情-架空历史-仙侠）
    - 第 5 列：连载/完结状态
    - 第 6 列：总字数
    - 第 7 列：**积分/热度值**（明文数字，如 123,867,200）
- **抓取要点**：
  - 使用 httpx 异步抓取，响应文本必须以 .content.decode("gb18030", errors="ignore") 解码；
  - 使用 
e.finditer 或轻量 HTML 解析器解析 <tr> 行中的 <td>，提取精度达 100%。

## 六、落地行动方案（M1 采集层规范）

根据上述调研结论，后续 Milestone 1（M1 采集层开发）严格按以下技术规格落地：

1. **模块架构**：在 pp/services/hotradar_fetcher.py 实现统一抽象基类 BaseRankFetcher 与三个平台专用子类：
   - QidianRankFetcher
   - FanqieRankFetcher
   - JjwxRankFetcher
2. **输出契约归一化**：
   每个 Fetcher 统一返回标准模型字典列表：
   `python
   {
       "platform": "起点",      # 起点 / 番茄 / 晋江
       "title": "夜无疆",        # 书名
       "rank": 1,               # 榜单排位
       "genre_tags": ["玄幻", "东方玄幻"],  # 题材标签数组
       "heat": 100000,          # 归一化热度或平台积分/在读数
       "author": "辰东",        # 作者（元数据可选）
   }
   `
3. **防护与安全机制**：
   - 请求超时统一设为 10 秒；
   - 随机构造常见桌面/移动端 User-Agent，杜绝固定标识；
   - 调度层以「每 6 小时或每天刷新」为周期，并对用户手动「立即刷新」施加最少 60 秒的节流防护（Cooldown），严格避免触发目标网站 IP 封锁；
   - 数据写入 hot_topics 表，7 天后自动软删除/清理。
